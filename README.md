# وصل | Wasl Delivery Inbox

واجهة عربية لإدارة محادثات العملاء والمناديب في نظام توصيل، مرتبطة بتفاصيل الطلب. مبنية بـ JavaScript وVite، ومجهزة للعمل مع Supabase Auth وPostgres وStorage وRealtime.

## حالة المشروع

- **العرض التجريبي يعمل مباشرة** بدون إعداد Supabase؛ جميع الأسماء والطلبات فيه بيانات توضيحية، وتُحفظ تعديلاته في المتصفح.
- **تكامل Supabase موجود في الكود**، لكنه يحتاج مشروعاً مخصصاً، تطبيق ملف SQL، وحساب دخول، ومتغيرات البيئة قبل أن يصبح متصلاً فعلياً.
- **لا يحتاج XAMPP أو PHP.**

## التشغيل

تحتاج Node.js 22.12 أو أحدث (يوصى بـ Node 24).

```bash
git clone https://github.com/mohammedwaleedmousa/test.git
cd test
npm ci
npm run dev
```

افتح العنوان الذي يعرضه Vite. بدون متغيرات البيئة يفتح العرض التجريبي. للتأكد من المشروع:

```bash
npm test
npm run build
npm run preview
```

## تفعيل Supabase

1. أنشئ **مشروعاً مخصصاً لهذا التطبيق**. لا تنفذ المخطط داخل مشروع يحتوي على نظام آخر.
2. نفّذ [supabase/schema.sql](supabase/schema.sql) مرة واحدة من SQL Editor. ينشئ الجداول والسياسات وحاوية الصور الخاصة، ويضيف الجداول إلى Realtime publication الموجودة.
3. من Authentication → Users أضف مستخدم دخول. إنشاء الحسابات ليس متاحاً من هذه الواجهة؛ لا توجد كلمة مرور افتراضية في المشروع.
4. انسخ `.env.example` إلى `.env` وأدخل **Project URL** و**Publishable key** فقط:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_YOUR_PUBLIC_KEY
```

5. أعد تشغيل Vite، ثم سجّل الدخول بالبريد وكلمة المرور اللذين أنشأتهما. يبدأ الصندوق السحابي فارغاً؛ لا يتم نسخ البيانات التجريبية تلقائياً إلى قاعدة البيانات.
6. عند النشر على Vercel أو استضافة ثابتة أخرى: أمر البناء `npm run build` ومجلد النتيجة `dist`. عرّف المتغيرين في إعدادات الاستضافة وأعد البناء بعد تغييرهما.

متغيرات `VITE_` تظهر في الواجهة، لذلك لا تستخدم `service_role` أو `sb_secret_` أو رمز GitHub فيها. `.env` و`node_modules` و`dist` مستثناة من Git.

## الوظائف

- واجهة RTL متجاوبة: قائمة المحادثات، الرسائل، وتفاصيل الطلب والمندوب والدفع.
- البحث في الأسماء وأرقام الطلبات والرسائل المحملة، وفلاتر العملاء والمناديب وغير المقروءة.
- إنشاء محادثة، إرسال رسالة أو صورة، ردود سريعة ورموز تعبيرية.
- حالات: مفتوحة، قيد المتابعة، تم الحل؛ مع إمكانية إعادة الفتح.
- تنزيل سجل المحادثة نصياً.
- في الوضع السحابي: تسجيل الدخول والخروج، حفظ البيانات، وتحديثات Realtime بين الأجهزة المسجلة **بالحساب نفسه**.
- صور خاصة بروابط موقعة قصيرة المدة، وتجديدها أثناء الاستخدام.
- عند فشل الحفظ لا تُعتبر الرسالة مرسلة، ويظل النص والمرفق لإعادة المحاولة.

## نموذج الوصول والحدود الحالية

هذه **نسخة أولية لصندوق موظف مستقل**، وليست نظام مراسلة متعدد الأطراف مكتمل الصلاحيات:

- كل مستخدم يرى محادثاته فقط عبر `owner_id` وRLS. لا يُشارك الصندوق بين حسابات مختلفة.
- العميل والمندوب في قائمة المحادثات هما جهتا اتصال، وليسا حسابي دخول مرتبطين تلقائياً.
- الواجهة تُنشئ الرسائل الصادرة فقط. استقبال الرسائل الواردة يحتاج تكاملاً موثوقاً أو تطبيق عميل/مندوب مع نموذج عضوية مناسب. سياسات قاعدة البيانات تمنع انتحال الرسائل الواردة من المتصفح.
- الرسائل الواردة في العرض التجريبي أمثلة ثابتة. لا توجد ردود آلية مزيفة في الوضع السحابي.
- تعرض النسخة آخر 100 محادثة وآخر 200 رسالة لكل محادثة. لا توجد واجهة تحميل التاريخ الأقدم بعد.
- حالة التواجد للعميل غير متاحة في الوضع السحابي؛ أمثلة التواجد محصورة في العرض التجريبي.
- تفاصيل الطلب في هذه المرحلة لقطة بيانات داخل المحادثة؛ الربط بمخزون أو طلبات شركة فعلية يحتاج واجهة النظام الأصلي.

## التحقق

الاختبارات المحلية تفحص تنفيذ المخطط، عزل حسابين، منع انتحال الوارد وتغيير المالك، خصوصية الصور، وصلاحيات الزائر. تختبر إعدادات العميل أيضاً وتمنع استخدام المفاتيح السرية وعناوين الصور غير الموثوقة. هذه اختبارات محلية بعقود Supabase مصغرة؛ لا تستبدل التحقق من Auth وStorage وRealtime على مشروع Supabase الحقيقي بعد الإعداد.
